# 批量回测性能问题分析

## 现象

- 主程序单次回测：~70s
- 批量并行回测（默认并发6）：200-600s（慢 3-8 倍）

---

## 根因分析

### 🔴 根因 1：任务提交延迟 `task_delay_s` （贡献最大）

**位置**：`engine.py:953-967` + `app.py:54`（默认 1.6 秒）

```python
# run_tasks_concurrently()
for i, row in enumerate(rows):
    executor.submit(run_one_task, ...)
    time.sleep(1.6)   # 每提交一个任务等 1.6 秒
```

| 任务数 | 提交耗时 | 总耗时（含最后任务执行70s） |
|--------|---------|-------------------------|
| 50    | 78s     | ~148s                   |
| 100   | 158s    | ~228s                   |
| 300   | 478s    | ~548s                   |

任务的提交延迟不应该在**提交阶段**（ThreadPoolExecutor 内部有队列），而应该在任务**执行完成后**控制速率。

---

### 🔴 根因 2：多线程写同一个 CSV 文件产生 I/O 争抢

**位置**：`engine.py:323-331` (`append_output_row`)

- 6 个线程同时 `open(output_csv, "a")` → `PermissionError` 频发
- 每次碰撞重试 `time.sleep(1.0)`，最多 10 次
- `os.fsync()` 强制同步刷盘，多线程下完全串行化

---

### 🟡 根因 3：后端 LLM 调用爆炸

**位置**：`graph_setup.py:121`（后端并行执行 3 个 AI agent）

- 前端 6 并发 × 后端每个请求内又 3 并发（Indicator/Pattern/Trend）= **18 个 LLM 请求同时打 API**
- LLM 提供商限流（429）→ 触发 `_post_with_retry` 指数退避（0.5s → 1s → 2s → 4s → ...）
- 进一步拖慢整体

---

### 🟡 根因 4：后端全局锁排队

- `id_manager.py:48`：`ResultIDManager` 用全局 `threading.Lock()` 串行生成 ID
- `analysis_log.py:20`：`AnalysisLogger` 用全局 `_log_lock` 串行写日志
- 高并发下累积开销不可忽略

---

### 🟠 根因 5：每次请求新建 4 个 LLM 客户端

- `analyze.py:340` 每次请求 `new TradingEngine()` → 新建 4 个 `ChatOpenAI` 实例
- 无客户端复用/池化

---

## 修复建议（按优先级）

| 优先级 | 改动 | 位置 | 预期效果 |
|--------|------|------|---------|
| P0 | 移除/大幅降低 `task_delay_s`，延迟移到执行完成回调 | `engine.py` | 直接解决主体耗时 |
| P0 | 将 CSV 写入改为队列模式（单线程写入） | `engine.py` | 消除 I/O 争抢 |
| P1 | 去除 `os.fsync` | `engine.py:append_output_row` | 减少单次写入耗时 |
| P1 | 后端限制 LLM 并发数（`asyncio.Semaphore(3~5)`） | `trading_engine.py` | 避免 LLM 限流 |
| P2 | 后端 LLM 客户端单例复用 | `trading_engine.py` | 减少初始化开销 |
| P3 | 考虑 `ProcessPoolExecutor` 替代 `ThreadPoolExecutor` | `engine.py` | 避免 GIL 争用 |

---

## 快速修复（3 处改动，预期总耗时降至 70-100s）

1. `app.py:54`：`task_delay` 默认值 `1.6` → `0`
2. `engine.py:331`：删除 `os.fsync(f.fileno())`
3. `engine.py:323-331`：`append_output_row` 改为线程安全的队列写入模式
